# TVSP-2026-001: build-denied placement can mutate a spawner stack

**Author:** Toprak Eker ([@toprakeker](https://github.com/toprakeker)), TovekSpawners maintainer. Analysis, patch implementation, and tests were assisted by OpenAI Codex.

**Date:** 7 November 2026.  
**Type:** Maintainer-authored security advisory. This is not an independently accepted third-party disclosure.  
**Severity:** Low (qualitative assessment; no CVSS score assigned).  
**CVE / GHSA:** None assigned. The identifier above is local to this project.

## Summary and impact

`SpawnerListener.onPlace` previously relied on `ignoreCancelled = true` but did not check `BlockPlaceEvent.canBuild()`. Bukkit exposes cancellation and build permission as separate flags. An event can have `isCancelled() == false` and `canBuild() == false`, for example when the server denies building in a protected area.

When a denied placement is against a compatible existing spawner below its stack limit, the handler increments the existing spawner's persistent stack count and consumes one item from a survival player's hand. The attempted block placement being denied does not undo those plugin side effects. This permits an unauthorized world-state modification under the stated event conditions. The same missing guard also allowed scheduling the fresh-placement callback for a build-denied event.

This is a game-world build-permission issue. It does not establish remote code execution, access to server files, or a bypass of every region-protection plugin. A plugin that cancels the event before this listener runs already prevents this particular path.

## Affected source and fix

- The missing build-permission guard is present in the released `v1.0.1` source (confirmed by source inspection).
- The executable regression reproduction used pre-patch main revision [`2e46cf24049d8ba338e90378f48d545c603d420b`](https://github.com/toprakeker/TovekSpawners/tree/2e46cf24049d8ba338e90378f48d545c603d420b), whose source version was `1.0.2`.
- Source fix: [`910e2ec398f7487da1c5fd97f3343749fc45a2a5`](https://github.com/toprakeker/TovekSpawners/commit/910e2ec398f7487da1c5fd97f3343749fc45a2a5), preparing version `1.0.3`.

Other historical versions were not exhaustively tested.

## Reproduction and validation

The regression uses real Bukkit `BlockPlaceEvent` objects with mocked plugin, world, inventory, and player dependencies; it does not contact a live Minecraft server.

1. Configure a mocked existing zombie spawner at count 3 with maximum count 50, and a survival player holding a matching spawner item.
2. Construct the event with `canBuild = false` and confirm that it is not cancelled.
3. Invoke the production `SpawnerListener.onPlace` method.
4. Assert that no stack count changes, item consumption, player side effects, or scheduled world writes occur.

Against the unpatched listener, the regression failed because `setStackCount` was invoked despite the build denial. Against the patched listener, all six placement-protection tests passed. The full `clean build` passed with 8 tests total, using Temurin Java 21 and Gradle 8.14.3.

Tests cover denied stacking, denied fresh placement, already-cancelled placement, normal permitted stacking, and late build denial or cancellation before a queued fresh-placement callback executes. The existing formatting test now calls production normalization rather than duplicating its logic with the system locale.

Run with Java 21:

```sh
./gradlew clean build --no-daemon --no-watch-fs
```

See [PlacementProtectionTest.java](../../src/test/java/dev/toprak/spawners/PlacementProtectionTest.java).

## Remediation and limits

The fix returns before any placement side effects if either cancellation or build denial is present. The deferred fresh-placement task checks both flags again before writing world state.

If upgrading immediately is not possible, administrators should ensure their protection listener cancels denied placement events before TovekSpawners' `HIGH` handler runs, or disable the plugin in the affected environment. Do not assume that the `canBuild` flag alone is sufficient on the affected code.

This is a focused fix, not a comprehensive protection-plugin compatibility audit. In particular, the tests do not establish that all immediate stack operations respect decisions made by later event handlers. No live-server compatibility certification is claimed.
